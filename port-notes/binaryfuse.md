# Port notes: `binaryfuse` (Go `FastFilter/xorfilter@v0.5.1` → `src/binaryfuse.rs`)

## Scope and API mapping

| Go | Rust |
|----|------|
| `xorfilter.BinaryFuse[uint16]` | `binaryfuse::BinaryFuse16` (pub fields `seed`, `segment_length`, `segment_length_mask`, `segment_count`, `segment_count_length`, `fingerprints: Vec<u16>`; `Clone + Debug + PartialEq + Eq`) |
| `NewBinaryFuse[uint16](keys)` | `BinaryFuse16::new(&[u64]) -> Result<_, Error>` |
| `(*BinaryFuse[T]).Contains` | `contains(&self, u64) -> bool` |
| `buildBinaryFuse` | private `build` (verbatim port) |
| `initializeParameters` / `getHashFromHash` | private, same names (snake_case) |
| `splitmix64` / `murmur64` / `mixsplit` / `fingerprint` / `pruneDuplicates` | private, same names |
| `MaxIterations` (mutable pkg var, 1024) | `MAX_ITERATIONS` const |
| `packstore.buildFilterSection` (serialize part) | `section_bytes(&self) -> Vec<u8>` |
| `packstore.parseFilterSection` | `BinaryFuse16::parse_section(&[u8]) -> Result<_, Error>` |
| `packstore.filterHeaderSize` (29) | `SECTION_HEADER_SIZE` |
| `packstore.filterTypeBinaryFuse16` (1) | `SECTION_TYPE_BINARY_FUSE16` |

The tail-dedup half of Go's `buildFilterSection` (`filterKey`, sort+compact)
stays in packstore where it lives in Go; this module serializes an existing
filter. The `BinaryFuseBuilder` buffer-reuse machinery was **not** ported: it
is a pure allocation optimization, proven result-identical by upstream's
`TestBinaryFuseBuilder`, and Go's amber-store-core only calls
`NewBinaryFuse`.

## Bit-compatibility measures (a reviewer should re-check these)

- **`buildBinaryFuse` ported line-for-line**: `rngcounter = 1` seed sequence,
  the `reverseOrder[size] = 1` placement sentinel, the `iterations % 4`
  segment-resize dance (gated on `4 < size < 1_000_000`), in-loop duplicate
  detection/undo, the branchless peeling (`is0/is1/is2` masks — note `is0`
  relies on **u8 wrap** of `found - 1`, ported with `wrapping_sub`), the
  failed-iteration `pruneDuplicates` (sort + dedup of the module's own copy;
  Go mutates the caller's slice), full state reset + reseed on error, and the
  reverse fingerprint-assignment loop. `size` is captured **before** pruning
  and never recomputed (a Go quirk: after pruning, leftover zero hashes are
  counted via the duplicate path) — preserved.
- **All wrap-reliant arithmetic uses `wrapping_*`** (`t2count` u8 counters,
  `segLenToMinusSegLenX2 = segLen ^ -(2*segLen)`, `other_index1/2` add/sub).
  Arithmetic that cannot overflow in-domain (geometry derivation, `h0 +
  segment_length`, dance `*2 + 2` / `/2 - 1`) is plain, so a debug build
  would panic loudly if the impossible happened, instead of wrapping
  silently.
- **`math.Log` ported from Go's portable FDLIBM source** (`go_log`, with
  `go_frexp` incl. `normalize`), NOT `f64::ln`. Constants keep Go's decimal
  spellings (`#[allow(clippy::excessive_precision)]`); the
  `go_math_bit_exact` test pins outputs to bit patterns generated by Go on
  the vectorgen platform (darwin/arm64, where `haveArchLog == false`, i.e.
  the portable path this port mirrors). Caveat: on **amd64** Go dispatches to
  `log_amd64.s` assembly; it implements the same FDLIBM method and is
  believed bit-identical, but if vectors were ever regenerated on amd64 and
  a filter case failed, look here first.
- **`math.Round` ported bit-twiddled** (`go_round`, half away from zero;
  `f64::round` shares the rule but the port removes doubt); **`math.Max`
  ported with its special cases** (`go_max`). `math.Floor` is NOT ported:
  floor is a correctly-rounded IEEE 754 operation, exact on every platform
  (`f64::floor`).
- `getHashFromHash` uses the 64×64→128 widening multiply's high word
  (`bits.Mul64` ↔ `u128` shift).

## Known answers embedded in unit tests

`go_reference_sections` cross-checks seed, all four geometry fields,
fingerprint count, and a CRC-32C over the full serialized section against
values captured from the pinned Go module (v0.5.1, run at port time on
darwin/arm64) for 31 cases: n ∈ {0..123456} spanning every geometry
breakpoint, duplicate-key inputs, and — importantly — deterministic inputs
that needed 2 and 3 construction iterations (`u64s(4, 11192)`,
`u64s(25, 1009)`: succeed with the dance's **halved** segment length kept;
`u64s(53|461, 3361)`: halved then **restored**). The final seed value encodes
the iteration count (seed #k = k-th splitmix64 output), so these prove the
retry and resize paths bit-match Go. `params_table_matches_go` ports
upstream's `TestBinaryFuseParams` table, pinning the log/round-derived
geometry for sizes 1 → 4,583,149.

## Go quirks preserved

- The **empty key set is not an error** (upstream `TestBinaryFuseN_ZeroSet`;
  the doc comment's "may return an error if the set is empty" is stale in Go
  too). It yields segment_length 4, segment_count 1, 12 zero fingerprints.
- `NewBinaryFuse` may mutate (sort/shorten) the caller's slice in Go; the
  Rust port copies instead — construction results are identical.
- `Contains` (and Go) index `Fingerprints` straight from the geometry
  fields: a hand-assembled inconsistent filter panics. `parse_section`
  validates the geometry invariants so untrusted section bytes cannot panic
  the read path (`footer.go`'s stated reason, same checks, same order:
  length → type byte → fp-count/length equation → geometry) — **plus one
  check Go is missing** (found in adversarial review): a crafted section
  with `segment_count == 0` (e.g. seg_len=4, mask=3, scl=0, fp_count=8)
  satisfies every equation `footer.go` checks, yet `Contains` then computes
  `h2 ∈ [2*seg_len, 3*seg_len)` against a `2*seg_len`-entry fingerprint
  array — an index-out-of-range panic on every lookup, in Go exactly as in
  a faithful Rust port. Real construction always yields `segment_count >= 1`
  (initializeParameters gives ≥ 1, and the `iterations % 4` dance
  round-trips `c → 2c+2 → c`), so rejecting it cannot refuse any Go-written
  section; PORTING.md's "never panic on untrusted input" hard rule (and
  footer.go's own comment) make rejection the correct behavior. This is the
  module's one intentional strictness divergence; the geometry bound proof:
  with seg_count ≥ 1, `h0 < scl`, and XOR by `< seg_len` stays inside a
  seg_len-aligned block, so `h2 < scl + 2*seg_len = fp_count`. Pinned by
  `parse_section_rejects_zero_segment_count`. If the Go side is ever
  patched, add `segCount == 0` to `parseFilterSection`'s switch.
- Degenerate regime, documented divergence: for > ~3.8e9 keys Go's
  `uint32(math.Round(...))` float→int conversion is itself
  implementation-specific (wraps on amd64, saturates on arm64); Rust `as`
  saturates. Unreachable for packstore (segments hold far fewer keys) and
  unusable anyway (≥ 8 GiB of fingerprints).

## Errors

`Error::TooManyIterations` (Display exactly Go's `"too many iterations"`;
practically unreachable — cosmic-ray territory) and `Error::Corrupt(String)`
with `is_corrupt()`. `Corrupt`'s Display is the bare detail text from
`footer.go` (`"filter section too short: N bytes"`, `"unknown filter type
T"`, `"filter section is N bytes, want M"`, `"filter geometry invalid"`);
Go renders these wrapped as `"amberpack: corrupt pack data: <detail>"` — the
packstore port should add its `ErrCorrupt` prefix when wrapping, and map
`is_corrupt()` to its corrupt classification.

## Tests

- Unit (`src/binaryfuse.rs`, 14): upstream's zero-set and both
  duplicate-keys tests ported verbatim; contains-all across sizes 0–32 and
  every geometry breakpoint (incl. 0/1/2/3 keys); Go known-answer sections
  (above); params table; go-math bit pins; determinism; FP-rate sanity;
  section round-trip; parse validation order + exact error text; the
  zero-segment-count rejection (reviewer addition, see quirks above).
- Reviewer re-verification (2026-08-08): all 31 known-answer cases were
  independently regenerated with the real pinned Go module
  (`go run` against `FastFilter/xorfilter@v0.5.1`, darwin/arm64) — seed,
  geometry, fingerprint count, and section CRC-32C all match, including the
  iteration-2/3 dance and duplicate cases the golden vectors don't cover.
  The `params_table_matches_go` table was checked row-by-row against
  upstream `TestBinaryFuseParams`. Go's `math.Log`/`Frexp`(+`normalize`)/
  `Round`/`Max` sources were re-read against `go_log`/`go_frexp`/`go_round`/
  `go_max`: constants and special-case order match exactly.
- Golden (`tests/golden_binaryfuse.rs`): `filters.json` per VECTORS.md —
  build over `u64s(seed, n)` dedup+sorted, compare section BLAKE3 (+ exact
  hex for n ≤ 100), then parse round-trip and contains-all. **Vectors were
  present and pass** (all 8 cases). Verified green both with and without
  `AMBER_GOLDEN_OPTIONAL=1`.
